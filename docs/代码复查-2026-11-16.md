## 1. 空值幂等键与标准 Transport 的重发规则不一致

代码位置：[请求头构造](../internal/runner/request.go)、[canRetry](../internal/runner/retry.go)。本轮对应代码位置为 request.go:29、retry.go:19。

Requests 的重试资格判断会对 Idempotency-Key 执行 TrimSpace；值为空或只有空白时，不认为具有幂等保护。但构造请求时仍把这个请求头原样放进 Header。

本机 Go 1.26.2 的 net/http.Request.isReplayable 判断请求能否重发时，会检查 Idempotency-Key 或 X-Idempotency-Key 是否存在，而不是验证其值是否非空。对于可重放正文，这可能使标准 Transport 认为 POST 可以重发。

复现条件：

1. 先发送一次请求并读完响应，让连接进入可复用状态。
2. 在同一个 Client 上发送 POST，请求正文可以重新打开，Requests 的 Retry 设置为 0。
3. 服务端第一次读完 POST 正文后直接关闭连接，没有返回响应。
4. 检查服务端实际收到 POST 的次数。

| 请求头 | 服务端收到的 POST 次数 | 最终结果 |
| --- | ---: | --- |
| 没有幂等键 | 1 | 返回错误 |
| Idempotency-Key 为空字符串 | 2 | 第二次返回成功 |
| Idempotency-Key 只有一个空格 | 2 | 第二次返回成功 |
| X-Idempotency-Key 为空字符串 | 2 | 第二次返回成功 |

这里是 net/http.Transport 对已复用连接的透明重发，不是 Execute 的重试循环执行了第二轮。Retry=0 只控制当前包显式执行的各轮尝试，不能直接理解为线上只会发送一次 HTTP 请求。

影响：如果调用方从空的业务标识生成幂等键，服务端实际没有有效的去重依据，创建订单等操作可能重复执行。有效的非空幂等键也需要服务端真正实现去重。

建议：对两个幂等键头统一处理，空字符串或纯空白值在参数检查阶段拒绝，或从构造后的 Header 中移除；明确两个头在显式重试判断中的支持策略，并补齐上述复现矩阵。继续在文档中说明显式重试与标准 Transport 重发的区别。

## 2. 默认脱敏的字段规范化分配过大

代码位置：[logging/redact.go](../logging/redact.go)，sensitive 函数约第 90 行。

当前 normalize 每次执行都会创建 strings.NewReplacer。每处理一个 JSON 字段，先规范化字段名，再逐项重新规范化 SensitiveFields。字段和自定义规则较多时，这个构造过程被反复执行。

临时基准直接调用实际的 DefaultRedactor.RedactRequest，输入为 2701 字节、包含 300 个普通字段的完整 JSON，结果仍为有效 JSON。使用本机 Go 1.26.2，得到：

| 自定义敏感字段数量 | 每次累计堆分配 | 每次分配次数 |
| ---: | ---: | ---: |
| 0 | 2,101,293 B，约 2.10 MB | 2,437 |
| 2（mobile、id_card） | 6,149,973 B，约 6.15 MB | 5,144 |

这些数字是一次脱敏操作的累计分配量，不是每条日志长期保留的内存。请求和响应都启用正文采集时，可能分别付出这类开销；重试还会继续放大。正文采集上限较小，并不意味着脱敏过程的临时分配同样小。

影响：增加 CPU 与垃圾回收压力，高并发记录小型 JSON 时也可能出现明显的性能损失和内存峰值。

建议：复用固定的字符替换器，或采用轻量的规范化函数；自定义字段名在遍历正文前规范化一次，形成只读匹配集合。保留现有大小写及标点匹配语义、递归处理和快照隔离，并用相同输入比较修改前后的 B/op、allocs/op。

## 3. 实际构建与验证工具链需要更新安全补丁

项目 [go.mod](../go.mod) 声明的最低版本是 Go 1.26.2，本机本轮验证也使用 Go 1.26.2。

截至 2026-11-16，[Go 官方发布记录](https://go.dev/doc/devel/release) 已发布 Go 1.26.11；1.26.2 之后的同分支版本包含 net/http、crypto/tls、crypto/x509 等安全修复。因此，最低主版本升级到 1.26 并不等于已经包含后续安全补丁。

建议：开发验证、CI 与正式构建使用维护中的最新补丁版本。当前继续使用 1.26 分支时，应更新到已发布的 1.26.11 或后续补丁。go.mod 的版本只是最低要求，是否提高最低版本可以单独决定；实际构建工具链应及时更新。

本轮没有修改 Go 版本或项目依赖。由于漏洞扫描工具下载失败，也没有对各个公告在当前调用路径上的可达性作完整判断。

## 4. 公网地址分类存在特殊用途地址漏项

代码位置：[internal/core/network_policy.go](../internal/core/network_policy.go)，reservedNetworks 与 publicAddress，约第 70、81 行。

临时测试通过 Go overlay 调用实际分类函数，没有修改项目源文件，观察到：

```text
publicAddress(3fff::1)     = true
publicAddress(5f00::1)     = true
publicAddress(192.88.99.2) = true
```

这些地址对应的 IANA 记录并不具有 Globally Reachable 属性：

| 地址或范围 | 注册用途 | 来源 |
| --- | --- | --- |
| 3fff::/20 | 文档用途 | [IANA IPv6 注册表](https://www.iana.org/assignments/iana-ipv6-special-registry/) |
| 5f00::/16 | SRv6 SID 用途 | [IANA IPv6 注册表](https://www.iana.org/assignments/iana-ipv6-special-registry/) |
| 192.88.99.2/32 | 6a44-relay anycast | [IANA IPv4 注册表](https://www.iana.org/assignments/iana-ipv4-special-registry/) |

IsGlobalUnicast 不能单独证明一个地址适合作为公网目标；当前实现补充了部分排除网段，但表并不完整。

影响：NewPublicClient 所依赖的公网判断可能放行部分不应放行的特殊地址。是否能成功连接还取决于实际路由环境，本轮没有据此声称能够访问任意内网地址。

建议：明确公网地址判定策略，至少补齐这些已明确的非全球可达地址，记录规则来源和维护日期，并增加分类回归用例。继续保留实际拨号 IP 检查、DNS 结果校验及 AllowedHosts 控制。

## 5. 空正文未统一保持 http.NoBody 语义

代码位置：[bodyPlan.request](../internal/runner/request.go)，约第 231 行；[ReadRequestLimit](../internal/lz/http_body.go)，约第 52 行。

两条路径已复现：

1. 合法的 BodyFactory 返回 io.NopCloser(strings.NewReader(""))、长度 0 和 nil 错误。当前请求设置了 ContentLength=0，但 Body 为非空对象，HTTP/1.1 序列化结果使用 chunked。
2. 原本使用 http.NoBody 的空请求，经 pf.ReadRequestBody 读取并恢复后，Body 被替换为普通的空 Reader；同一个请求的 HTTP/1.1 序列化从不使用 chunked 变为使用 chunked。

```text
factory_length_0_empty_body_chunked=true
restore_empty_body_before_chunked=false after_chunked=true
```

原因：Go 对非 nil、非 http.NoBody 且 ContentLength=0 的请求正文，会按未知长度处理。

影响：调用者明确提供了空正文，却可能得到不同的传输格式；要求显式空正文长度、校验请求签名或对 chunked 支持有限的服务可能因此拒绝请求。此处讨论的是 HTTP/1.1 的传输行为。

建议：工厂和 BodySource 的已知零长度结果统一验证并转换成 http.NoBody，正确关闭原流；读取恢复工具对完整空正文同样保留 http.NoBody 语义，GetBody 返回值也一致处理。补充无显式 Content-Length、工厂返回空 Reader、NoBody 及恢复后序列化的测试。

## 6. 回调 panic 时最终日志可能误报成功

代码位置：[Execute 的最终汇总](../internal/runner/execute.go)，约第 81 行；URLPolicy 调用约第 138 行。

当前最终 defer 通过 err==nil 决定标记 PhaseComplete。URLPolicy、SuccessStatus、RetryDecider、Backoff 等回调没有统一的 panic 转换约定；例如 URLPolicy 在返回前直接 panic，命名返回值 err 仍可能为 nil。

临时探针在调用方恢复 panic，并捕获 OnEnd，结果为：

```text
callback_panic=true
final_phase=complete
final_err_nil=true
attempts=0
```

影响：请求未执行成功，日志却显示成功完成。调用方即使通过自己的异常恢复机制处理了 panic，请求日志也可能误导排查。

建议：最终汇总区分正常返回和异常退出；如果约定继续传播 panic，先记录异常结束状态，再继续传播，不把成功事件发出去。对于需要转换为 error 的业务扩展回调，统一规定处理方式。无论选择哪种策略，都保证已经接管的资源得到清理。

## 7. 公网检查与 TLS 配置的组合边界需要完善

这是 API 设计限制，不是已复现的网络策略绕过。

代码位置：[validateClient](../internal/core/client.go)，约第 66 行；[ClientParam](../tn/client.go)。

启用 NetworkPolicy 后，自定义 Transport 会被拒绝。这能避免自定义拨号行为绕过 IP 检查，但 ClientParam 也没有单独的 TLS 配置入口。

因此，需要同时启用公网检查和自定义根证书、客户端证书（双向 TLS）时，使用者无法通过当前正常配置方式组合完成。临时探针也确认 NewPublicClient 加自定义 TLS Transport 在创建阶段返回 ErrClientConfig。

建议：提供受控的 TLS 与连接参数配置，在库内部构造 Transport 并继续叠加实际 IP 检查。公网客户端继续保留禁用代理和受控拨号的规则，不以允许任意 Transport 的方式放开安全边界。

## 8. 匿名创建客户端仍存在隐式全局名称

这是目前已记录的 API 行为，作为第三方库仍值得重新评估。

代码位置：[NewClient](../internal/core/client.go)，约第 29 行。

SpaceName 为空时，当前会使用全局 master 名称。两个互不相关的模块如果分别调用：

```go
requests.NewClient(tn.ClientParam{Timeout: time.Second})
requests.NewClient(tn.ClientParam{Timeout: 2 * time.Second})
```

第二次调用会发生配置冲突。临时探针确认返回 ErrClientConfig，而不是创建两个独立客户端。

影响：虽然移除了默认全局 Limiter，不同模块仍可能在客户端创建阶段相互影响。这个问题不会让已经持有 Client 的每次 HTTP 调用都争用命名缓存锁，但会影响模块独立配置。

建议：考虑让空 SpaceName 表示创建独立客户端，只有显式名称才启用命名复用；共享默认 Client 继续通过 Api(nil, p) 明确使用。设计调整前，使用者可以采用 NewClientUncached 避免这类冲突。
