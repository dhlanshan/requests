## R3-01：部分早退路径没有复核并保留 Context 原因

代码位置：[Execute](../internal/runner/execute.go)，约第 138、168、238 行；[prepareBody](../internal/runner/request.go) 的首次打开流错误出口。

### 已复现的场景

| 场景 | 实际调用 Transport 次数 | 返回错误中可查询的 Context 标记 |
| --- | ---: | --- |
| 首次收到 503，RetryDecider 取消上游并返回 false | 1 | Canceled=false |
| 同样取消，但 RetryDecider 返回 true | 1 | Canceled=true，控制组 |
| RetryDecider 等到总期限结束后返回 false | 1 | DeadlineExceeded=false |
| 初始 URLPolicy 等到总期限结束后返回业务拒绝错误 | 0 | DeadlineExceeded=false，原始拒绝原因保留 |
| 不可重放 BodySource 在准备阶段等到总期限结束后返回打开失败 | 0 | DeadlineExceeded=false，原始打开失败原因保留 |

探针在回调中等待 ctx.Done()，没有依赖 sleep 来碰撞边界。RetryDecider 的两组取消实验仅切换返回值，就观察到了不同的错误分类结果。

### 原因与影响

RetryDecider 返回 false 后直接返回先前的失败错误，没有执行回调后的期限复核。初始 URLPolicy 失败和公共正文准备失败也存在直接早退。

请求没有因此被判为成功，也没有观察到多发下一轮。问题在于取消/超时已经发生，却无法通过 errors.Is(err, context.Canceled / DeadlineExceeded) 识别；调用方的取消统计、超时归因和错误分流会不一致。

### 修补方向

- 在上述回调返回或阶段失败后，读取仍有效的总 Context，并用已有 MergeContextError 保留原始原因、补上 Context 原因。
- RetryDecider 返回 false 的分支也要复核；不能只依靠进入 waitRetry 时检查取消。
- 保留 URLPolicy 的 ErrTargetBlocked 包装和正文准备阶段的原始错误，不用 Context 错误简单替换。
- 不在本函数主动 cancel 之后读取该 Context 来重写结果，不把前几轮失败累计到新的重试等待错误中。
- 添加取消与总期限的对照回归，同时断言原始原因、Context 标记和实际尝试数。

## R3-02：证书错误的禁止重试分类覆盖不完整

代码位置：[internal/runner/retry.go](../internal/runner/retry.go)，retryForbidden 第 54 行附近。

当前只匹配 UnknownAuthorityError、HostnameError、CertificateInvalidError 的值形式。errors.As 按实际错误类型的可赋值关系匹配；对应的指针形式不会被这些值变量接住。另外，系统根证书加载错误等没有进入当前禁止列表。

Go 的 [SystemRootsError](https://pkg.go.dev/crypto/x509#SystemRootsError) 表示系统根证书加载失败；标准 TLS 还会通过 [CertificateVerificationError](https://pkg.go.dev/crypto/tls#CertificateVerificationError) 表达握手中的证书验证失败。当前只枚举三个 x509 值类型，不能覆盖这些组合。

### 对照结果

设置 Retry=1，使用受控 RoundTripper 返回相应错误，比较默认策略与总返回 true 的 RetryDecider：

| 错误形式 | 默认策略尝试数 | 自定义决策尝试数 |
| --- | ---: | ---: |
| UnknownAuthorityError 值 | 1 | 1，决策函数不被调用 |
| UnknownAuthorityError 指针 | 1 | 2 |
| HostnameError 值 | 1 | 1，决策函数不被调用 |
| HostnameError 指针 | 1 | 2 |
| CertificateInvalidError 值 | 1 | 1，决策函数不被调用 |
| CertificateInvalidError 指针 | 1 | 2 |
| SystemRootsError | 1 | 2 |
| CertificateVerificationError 包装 SystemRootsError | 1 | 2 |

这里统计的是执行层调用 Transport 的次数。所有情况最终均返回失败；没有执行真实的坏证书 TLS 连接，也没有据此声称能绕过证书验证或重复提交 HTTPS 业务请求。

### 影响与建议

默认决策没有对这些漏项进行额外重试。只有配置了主动放行的 RetryDecider 时，才会出现表中额外尝试。这与现有文档“证书错误不能被自定义决策放行”的约定不一致，并会增加无效等待和连接尝试。

建议针对证书验证错误补齐分类：兼顾已有三种类型的值和指针形式，覆盖系统根证书错误，并识别标准 TLS 的证书验证包装。每种形式均增加“自定义决策总放行”的回归。握手中的临时网络故障仍按网络错误规则处理，证书验证分类与网络分类分别维护。

## 第一轮三项代码问题仍待修正

这三项不是本轮新增发现，当前静态复核确认相应实现尚未改变；原复现和影响见[第一轮报告](代码复查-2026-11-16.md)。

1. **特殊用途 IP 分类漏项。** reservedNetworks 没有补齐此前发现的 3fff::/20、5f00::/16 和 192.88.99.2/32 等明确特殊用途地址。建议维护有来源和日期的规则，并补齐地址分类回归。需要继续保留实际拨号 IP 校验。
2. **空正文语义。** bodyPlan.request 仍会把工厂返回的普通空 Reader 配上 ContentLength=0；pf 的读取恢复也将 NoBody 换成普通空 Reader。HTTP/1.1 可能改为 chunked。建议统一已知空正文、恢复流与 GetBody 的 NoBody 语义，并正确关闭原流。
3. **panic 后的结束日志。** Execute 最终 defer 仍以 err==nil 标记 complete；URLPolicy 等回调直接 panic 时，仍存在最终日志误报成功的路径。建议区分正常返回和异常退出，并明确是继续传播 panic 还是转成错误，同时完成资源清理。

建议将这三项和本轮两类 P2 汇总为下一批代码修补范围，避免继续分散遗留。

## 灵活性方面仍需决定的设计

- 公网检查与自定义根证书、客户端证书暂时不能通过正常配置组合。应提供受控的 TLS 配置入口，同时由内部 Transport 保留实际 IP 检查。
- 匿名 NewClient 仍使用全局 master，不同模块提交不同配置会冲突；NewClientUncached 是当前可用的独立构造入口。是否改为空名称创建独立实例，属于公开行为设计。

这两项当前已有明确行为和替代用法，不能与新发现的错误处理缺陷混为一类。

## 性能与并发复核

- Limiter=nil 时仍跳过共享预算与排队，不使用全局默认 Limiter。
- MaxConnsPerHost=0 仍保留不限制连接总数的配置语义；连接复用与空闲池继续由 Transport 管理。
- 请求执行期间不通过命名缓存查找 Client；缓存锁作用在构造与查找阶段。
- 正文重放、采集缓存和读取缓冲均按当前配置与实际并发占用资源；显式容量预算不是整个进程的严格内存上限。

本轮执行现有 BenchmarkApiSmallResponse，使用受控 RoundTripper、11 字节响应，不含真实网络、日志或业务校验。环境为 Apple M3 Max / darwin arm64 / Go 1.26.2，三次 benchtime=300ms 的结果：

| 项目 | 结果 |
| --- | --- |
| ns/op | 2183、2158、2119，中位数 2158，约 2.16 µs/次 |
| 累计分配 | 4033 B/op |
| 分配次数 | 40 allocs/op |

这个基准用于观察本地执行开销，不能单独说明真实网络吞吐或任意并发量下都无瓶颈。本轮没有发现需要与上述两类 P2 同列的新性能缺陷，也没有开展新的大规模连接压测。
