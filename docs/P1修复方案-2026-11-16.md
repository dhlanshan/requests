# 两项 P1 问题的修复方案与验证结果

- 日期：2026-11-16。
- 状态：已实施，并通过竞态回归、静态检查和修复前后的同口径分配基准。
- 范围：修复空白幂等键导致的意外重发、默认日志脱敏的过量临时分配。Go 版本及依赖没有调整，其他复查项仍按原报告后续处理。
- 关联：[原始复查报告](代码复查-2026-11-16.md)。

## 1. 空白幂等键导致 POST 意外重发

### 原因与目标

执行层原来只把非空白的 Idempotency-Key 视为重试依据，但构造 HTTP 请求时仍然发送空值。标准 Transport 对可重放请求的判断包括 Idempotency-Key / X-Idempotency-Key 是否存在；在复用连接发生特定故障时，即使执行层 Retry=0，也可能因此透明重发 POST。

目标是消除“没有有效业务幂等标识，却仅因空头存在而获准重发”的情况，同时保留有效幂等请求、正文重放和连接复用。

### 处理规则

选择移除空值，而不是让原先传空字符串的调用直接报参数错误。strings.TrimSpace 用于判断是否为空白，执行层不裁剪有效值。

| 输入 | 实际请求头 | 对非 GET/HEAD/OPTIONS 请求的显式重试资格 |
| --- | --- | --- |
| 两个幂等键都未提供 | 不添加 | 仅在 AllowUnsafeRetry=true 时放行 |
| 任一个键为空字符串或纯空白 | 删除对应键 | 空值不授予资格 |
| 任一个键含非空白值 | 保留有效值 | 可放行方法检查，仍需满足次数、错误类型、正文重放和期限等条件 |
| 重定向回调写入 nil 或零长度值切片 | 删除对应键，不能只保留一个无值的 map 项 | 不授予资格 |
| 重定向回调写入多个值，其中含空白 | 删除空白项，保留有效值的原文与顺序 | 至少有一个有效值才授予资格 |

两个头都按上述规则处理。初始请求头名由已有逻辑规范化，重定向清理也识别大小写变体。

### 执行位置与所有权

1. [NewRequest](../internal/runner/request.go) 复制 ApiParam.Header 到新 Request 后，调用 stripBlankIdempotencyKeys。只修改新请求，不删除调用方 map 中的项。
2. [canRetry](../internal/runner/retry.go) 对 Idempotency-Key 和 X-Idempotency-Key 使用一致的非空白判断；遍历有效值，不再局限于 Header.Get 的第一个值。
3. [policyClient](../internal/runner/policy.go) 在用户 CheckRedirect 和目标/跨源头检查之后，重新清理空白幂等键，再判断当前跳转是否仍具有重试资格，最后才交给 Transport。
4. 多值需要过滤时创建新的切片，不原地改写回调传入的值切片，避免污染外部配置。

跨源白名单仍然有效，清理掉的幂等键不会为了重试被自动补回。任何非安全方法跳转失去保护后，仍按原规则停止整次调用的后续显式重试。

### 行为变化和边界

- 空值调用继续正常构造请求，但服务端不再收到对应的空白幂等头。
- X-Idempotency-Key 的非空白值现在也能授予执行层的显式重试资格；之前只有标准 Transport 认可它。这一变化已同步到 ApiParam 注释、README 和架构文档。
- Retry 控制执行层的额外尝试次数。Retry=0 仍不等于禁止标准 Transport 的所有透明重发；有效幂等键和可重放正文仍可能触发它原有的重发规则。
- 幂等键需要服务端真正去重。没有新增“业务操作只会执行一次”的保证，也不生成业务幂等键。
- 自定义 Transport 在接管请求后自行修改请求头或重发的逻辑，仍由该扩展负责。

### 回归验证

新增 [idempotency_test.go](../idempotency_test.go)，并扩充 [redirect_safety_test.go](../redirect_safety_test.go)。

真实 HTTP/1.1 测试先预热连接，再让服务端完整读取首次 POST 正文并断开连接、不发送响应。测试验证首次 POST 确实复用了预热连接，避免场景未触发却误判通过。

| 场景，Retry=0 | 修复前服务端收到 POST 次数 | 修复后 |
| --- | ---: | ---: |
| 无幂等键 | 1，返回错误 | 1，返回错误 |
| Idempotency-Key 空字符串或纯空白 | 2，最终成功 | 1，返回错误 |
| X-Idempotency-Key 空字符串或纯空白 | 2，最终成功 | 1，返回错误 |
| 两个头同时为空白 | 2，最终成功 | 1，返回错误 |
| 任一个头含有效幂等键 | 2，最终成功 | 2，最终成功 |

该表仅描述上述响应丢失场景。有效键的两次传输是标准 Transport 的透明重发，执行层仍只执行一轮。

另有测试覆盖两个头的显式 503 重试、有效值原文保留、调用方 Header 隔离，以及重定向回调的 nil/空白/混合多值/非规范大小写清理；跨源丢键后停止重试的现有测试也扩展到了 X-Idempotency-Key。

## 2. 默认日志脱敏产生过量临时分配

### 原因与目标

原实现每判断一个 JSON 或表单键，就构造一次 strings.NewReplacer；比较自定义字段时，又为每个候选规则重复构造替换器、重复规范化字符串。字段数和规则数增加后，临时分配远大于采集到的正文。

目标是移除重复构造和重复处理规则的开销，保持原来的脱敏语义与并发使用方式。

### 实现方案

代码集中在 [logging/redact.go](../logging/redact.go)：

1. 将删除 -、_、. 的 strings.Replacer 提升为包内共享实例，字段规范化继续使用 strings.ToLower，保留原有 Unicode 大小写处理。
2. 每份有效 JSON / URL 表单正文在开始遍历前，将 SensitiveFields 规范化一次，生成只读匹配集合。
3. 每个正文键只规范化自身，再做内置敏感片段匹配及自定义字段的集合查询。
4. JSON 对象、数组与嵌套对象共用本份正文的同一个规则集合，不在递归时重建。
5. 不向 DefaultRedactor 写入缓存，不全局缓存业务字段，也不修改调用方的 SensitiveFields。规则集合随单次操作释放；固定替换器可以由标准库安全地并发使用。

这使自定义规则的规范化次数从“每个字段逐条重做”变为“每份正文逐条处理一次”，匹配时不再遍历所有自定义规则。

### 保留的脱敏与隔离规则

- 内置敏感片段匹配不变，自定义字段仍为规范化后精确匹配；自定义规则不能关闭内置规则。
- 字段名仍忽略大小写及 -、_、.，包括原来对空字段名的匹配语义。
- JSON 继续递归处理对象和数组，并保留 UseNumber 的数值处理。
- 表单继续按键处理，敏感键的全部值替换为脱敏标记。
- 非法、未知、截断或不完整正文仍按原规则省略。
- 请求与响应都使用优化后的处理路径，输入正文和 HTTP 数据隔离规则不变。
- 同一个 DefaultRedactor 可以并发复用，但配置及 SensitiveFields 仍应保持只读。

### 同口径基准

新增永久基准 [BenchmarkDefaultRedactorJSON](../logging/redact_test.go)。修复前后均使用这份基准，输入为 2701 字节、300 个普通字段的完整 JSON，调用实际 RedactRequest，包含 URL 处理、JSON 解码、匹配及重新编码。

环境为 Apple M3 Max / darwin arm64 / Go 1.26.2；非 race 构建，每组运行 3 次，benchtime=200ms。下表为中位数：

| 场景 | 修复前累计堆分配 | 修复后累计堆分配 | 分配减少 | 耗时，修复前 → 修复后 |
| --- | ---: | ---: | ---: | --- |
| 默认规则 | 2,101,708 B/op | 75,209 B/op | 96.42% | 362.458 µs → 85.243 µs |
| 额外配置 mobile、id_card | 6,150,124 B/op | 75,471 B/op | 98.77% | 836.409 µs → 87.306 µs |

每次分配次数分别从约 2437 / 5144 降为 1229 / 1232。这些是一次完整脱敏操作的累计分配，不是每条日志长期占用的内存；剩余分配包括 JSON 解析和编码。实际性能随正文、规则和运行环境变化，上述结果不是吞吐量承诺。

[并发回归测试](../logging/redact_test.go) 同时使用同一个配置处理请求和响应，覆盖 JSON/表单、数组嵌套、大小写与标点规范化、Unicode、自定义字段和内置字段，以及输入正文不被修改。已有的截断、非法正文、数值保留和日志快照隔离测试继续通过。

## 3. 验证命令与结果

以下命令使用本机 Go 1.26.2；本轮未升级工具链或依赖。

```sh
go test -race ./... -skip '^TestK1$' -count=1
go vet ./...
go test ./logging \
  -run '^TestDefaultRedactorStructuredRulesConcurrent$' \
  -bench '^BenchmarkDefaultRedactorJSON$' \
  -benchmem -benchtime=200ms -count=3
```

- 全项目竞态回归通过。TestK1 是既有外网测试，本轮继续跳过。
- go vet 通过。
- 新增幂等键测试在修复前复现失败，修复后全部通过。
- 脱敏并发测试及修复前后基准均已执行，结果如上。
- 本机沙箱默认不允许绑定端口；真实 HTTP 测试在获准的沙箱外运行，监听本机回环地址，不依赖外部服务。
