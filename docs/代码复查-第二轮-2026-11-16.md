## R2-01：返回最初站点时漏清理跨源 Referer

代码位置：[internal/runner/policy.go](../internal/runner/policy.go)，checkRedirectTarget 第 45 行附近。

### 条件与原因

需要显式开启 AllowCrossOriginRedirect。默认禁止跨源跳转时，这条链不会走通。

当前头部白名单清理位于 !sameOrigin(first, req.URL) 分支中，即只比较“目标与最初地址”。当 B 跳回最初地址 A 时，目标与 first 同源，于是没有执行清理。但这一跳实际从 B 到 A，标准 Client 自动生成的 Referer 仍来自 B 的最后一个 URL。

已用以下链条复现：

```text
A/start
  → B/entry
  → B/private?token=SYNTHETIC-FOREIGN-SECRET
  → A/final
```

模拟令牌由 B 的站内跳转产生，返回 A 的 Location 本身不包含该令牌；A 最后却收到了：

```text
Referer: http://B/private?token=SYNTHETIC-FOREIGN-SECRET
```

实际本地 HTTP 测试中，A、B 是不同端口的回环服务，确实在 A 的服务端观察到了上述 Header。独立控制流探针也确认：改为跳到第三个源 C 时，Referer 正常被清空，问题集中在返回 first 的路径。

### 影响与建议

使用默认跨源头白名单时，原本不允许携带 Referer，返回原站这一步却可能泄露另一站点 URL 中的 token、签名或其他查询参数。这里已验证 URL 查询参数的传递，没有推断任意 Authorization 或 Cookie 都会因此泄露。

建议分开处理两个判断：

1. 保留相对最初地址的跳转、正文和请求头限制。
2. 同时判断相邻两跳是否跨源，对 B→A 这种返回路径执行头部白名单清理。
3. 不要简单把所有 first 替换成 previous。标准 Client 会在后续跳转复制初始 Header；如果仅看相邻两跳，B→B 时可能跳过现有清理，重新带入初始自定义认证头。
4. 补充 A→B→B→A、A→B→C，以及显式允许 Referer 的对照用例，验证自定义凭证头也不会在中间站点重新出现。

## R2-02：单次超时覆盖永久错误，反而触发重试

代码位置：[internal/runner/execute.go](../internal/runner/execute.go)，第 203 行附近；[internal/validator/safe.go](../internal/validator/safe.go)，第 21 行附近。

### 原因

execute 在 perform 结束后，如果发现 attemptCtx.Err()!=nil，会直接用该超时错误替换 err，并重新计算 retry。原来错误链里的 ErrResponseWrite、ErrPermanent 等禁止重试依据因此丢失。

业务验证还有更早的一层覆盖：validator.Validate 的 defer 在 Context 到期时直接丢弃已经收到的验证错误，包括 tn.NoRetry 包装。只修改 execute 无法恢复这个已经丢失的原因。

### 对照结果

探针设置 Retry=1、SingleTimeout=10ms、总 Timeout=1s。Writer 或验证器通过等待 ctx.Done() 在单次期限结束后立即返回，不依赖 sleep 碰运气。

| 场景 | 执行层调用 Transport 次数 | 最终 errors.Is 结果 |
| --- | ---: | --- |
| Writer 在超时前返回“写入 0 字节 + 固定错误” | 1 | ErrResponseWrite=true，原始原因=true |
| 同一个 Writer 在单次期限到达时返回同样错误 | 2 | ErrResponseWrite=false，原始原因=false，DeadlineExceeded=true |
| 验证器在超时前返回 tn.NoRetry(固定错误) | 1 | ErrPermanent=true，原始原因=true |
| 验证器在单次期限到达时返回同样的 NoRetry 错误 | 2 | ErrPermanent=false，原始原因=false，DeadlineExceeded=true |

验证器场景开启 EnableValid 和 RetryValidation。Writer 场景写入字节数为 0；若已写出字节，现有 written>0 规则仍会阻止后续重试，本轮没有声称该规则失效。额外尝试仍受 Retry 和总期限约束，不是无限重试。

### 影响与建议

当前文档约定 Writer 写入错误和 NoRetry 标记不能被重试策略放行。期限边界处实际会再次调用下游，且调用方无法再通过 errors.Is 找到原始原因。

建议：

- 原本成功、事后发现超时时，转换为超时失败。
- 原本已经失败时保留错误链，并附加超时原因，例如合并错误；使用保留后的禁止重试标记作判断。
- 同步处理验证器与 execute 的各处期限检查，避免某一层提前抹掉错误。
- 总期限到达或上游取消仍应终止调用，不能因为保留原始错误而继续运行。
- 新增“永久错误与单次超时同时发生”的回归，验证尝试数为 1，并同时保留原始错误标记和超时信息。

## R2-03：中间件可比较性校验不能阻止动态值 panic

代码位置：[mdw/chain.go](../mdw/chain.go)，第 53、65、71 行附近。

当前校验使用 reflect.Type.Comparable，随后直接将 Middleware 作为 map 的 key。结构体中有 any/interface 字段时，类型本身可以通过该检查，但字段实际保存的切片、map 等值可能使整个值无法比较或哈希。Go 官方也区分了[类型可比较性](https://pkg.go.dev/reflect#Type.Comparable)与[实际值可比较性](https://pkg.go.dev/reflect#Value.Comparable)。

探针中的中间件具有以下形状，并实现正常的 RoundTrip、SetTransport、Name、Clone 方法：

```go
type valueMiddleware struct {
    metadata any              // 实际保存 []string
    next     *http.RoundTripper
}
```

调用 NewClientUncached 后，构造器并未返回 ErrClientConfig，而是发生：

```text
hash of unhashable type: []string
```

这是构造阶段的 map 操作触发的 panic，中间件方法没有主动 panic，也没有发送 HTTP 请求。

建议在任何 map 访问及接口比较之前，使用 reflect.ValueOf(mw).Comparable() 检查实际值；原型与 Clone 结果都要检查。不能安全比较的值应返回配置错误，提示使用指针实例。这里不需要禁止中间件指针内部持有切片，因为指针本身具有可比较身份。

## R2-04：最终 StatusCode 与当前注释约定不一致

代码位置：[internal/runner/execute.go](../internal/runner/execute.go)，第 200 行附近；[logging/events.go](../logging/events.go)，CallResult 第 142 行附近。

CallResult 当前注释为“StatusCode 是最近一次收到的 HTTP 响应状态；从未收到响应时为 0”。

控制探针：

```text
第 1 次尝试：收到 HTTP 503
第 2 次尝试：网络读取错误，没有收到响应
最终结果：AttemptCount=2，StatusCode=0
```

原因是每次 perform 返回的 status 都直接覆盖外部变量；无响应返回的 0 清掉了上一轮的 503。若第二轮在 BodyFactory 打开阶段失败，外部 status 又会保留上一轮状态，行为也不统一。

建议按现有注释保留最近一个真实收到的 HTTP 状态，只有从未收到响应才为 0；单轮是否收到响应仍由 AttemptResult.Response 表达。如果希望改为“最后一次尝试的状态”，也可以选择该语义，但必须统一实现、注释和示例。这是观测字段的契约问题，不意味着网络错误被当作成功。
